# AI video generation platform with BYOK Replicate integration

BrainFog.mov is a greenfield Next.js 16 application that lets users generate short-form "brainrot" videos by sending prompts to Replicate's prediction API. The user supplies their own API key (BYOK model), which is stored in `localStorage` on the client side and passed through BrainFog's API routes to Replicate. The platform includes a marketing site (landing + pricing), credential and Google OAuth authentication via NextAuth.js v4, and a dashboard with generation, history, and settings pages. Client-side localStorage handles all persistent state: API keys, video history, and usage tracking.

**Watch for:** API keys transmitted in request bodies without auth protection on the generation endpoints (confirmed). Plaintext password comparison and in-memory user store make the auth layer demo-only but the code ships a committed `.env.local` with a real `NEXTAUTH_SECRET` (confirmed). Client-side daily usage limits are trivially bypassed (confirmed).

## High-level view

Authentication uses NextAuth.js with an in-memory user array and plaintext password comparison. The `NEXTAUTH_SECRET` is committed to the repository in `.env.local`, and passwords are stored and compared without hashing. This is a hard blocker for any deployment beyond local demo.

The video generation pipeline proxies user-supplied Replicate API keys through Next.js API routes. The API routes at `/api/generate` and `/api/generate/[id]` have no session check — anyone who can reach these endpoints can use them as an open proxy to Replicate with any key.

All state persistence (API keys, video history, usage quotas) lives in localStorage. The daily generation limit is enforced purely client-side, meaning a user can reset it by clearing storage or calling the API directly. Rate limiting is effectively absent.

## Unauthenticated API routes as Replicate proxy

The generation endpoints in `src/app/api/generate/route.ts` and `src/app/api/generate/[id]/route.ts` accept requests from anyone. The middleware in `src/middleware.ts` only protects `/dashboard/:path*`, leaving `/api/generate` wide open.

```
// middleware.ts
export const config = {
  matcher: ["/dashboard/:path*"],
};
```

Any unauthenticated HTTP client can POST to `/api/generate` with a valid Replicate key and use BrainFog as a cost-free proxy. The fix: extend the middleware matcher to include `/api/generate/:path*`, or add a `getServerSession` check inside each route handler.

## API key lifecycle and exposure surface

The Replicate API key flows: localStorage (client) -> JSON body (POST `/api/generate`) -> server-side `fetch` to Replicate. On the status polling path, the key travels in an `X-Api-Key` header from client to the Next.js route, then to Replicate.

The key sits unencrypted in localStorage, accessible to any XSS payload. Because there's no authenticated session on the API routes, any script that can reach the API can use a key found in a request. Next.js doesn't enforce CORS restrictions on API routes by default, widening this surface.

The settings page shows a green "Valid" indicator whenever `replicateKey` is non-empty, with no actual validation against the Replicate API — this could mislead users into thinking their key was verified when it's merely non-blank.

## Committed secrets and environment handling

The `.gitignore` file includes `.env*.local`, which should prevent `.env.local` from being tracked. However, the file is present in the repository and contains:

```
NEXTAUTH_SECRET=brainfog-dev-secret-change-in-production
```

If this was committed before the gitignore entry was added, it's now in git history permanently. Remove it from tracking and rotate the secret.

## In-memory auth and plaintext passwords

`src/lib/auth.ts` maintains a `users: StoredUser[]` array in module scope. Passwords are stored and compared as plaintext strings. The authorize callback does `user.password !== credentials.password`. The signup route stores the password as-is via `addUser`.

The app deploys a full authentication UX (sign-in, sign-up, session management, middleware protection) that gives users the impression of real security while offering none. If a user reuses a password, it's stored in cleartext in server memory.

## Client-side usage enforcement

```typescript
export function getDailyLimit(): number {
  return 3;
}
```

`getUsageToday()` reads from localStorage keyed by today's date string. The generation page checks `isOverLimit` before enabling the submit button, but since the API routes don't enforce any limit, a user can curl the endpoint without restriction. The pricing page advertises tier-based limits (3/day free, 50/day pro, unlimited business) that have no backend enforcement.

## Polling lifecycle gap on unmount

`useVideoGeneration` sets up a 2-second polling interval via `setInterval`. Cleanup happens on unmount and on terminal states. If the component unmounts while a fetch is in-flight, the response callback can still call `setStatus` on an unmounted component. React 19 tolerates this better than earlier versions, but it's a potential source of stale state updates if the user navigates away mid-generation.

## Hardcoded model version and frame calculation

The Replicate integration hardcodes a model version hash:

```typescript
version: "c0a4015dc68a6da82e26aa02e1b0704c2634816495550a1e4e22e10b8e4b02c4",
```

The `num_frames: params.duration * 8` calculation assumes 8 fps. This is model-specific and will silently produce wrong durations if the model version changes or is updated. Consider extracting this as a named constant with a comment tying it to the model spec.

## No test coverage

The project has zero test files. The auth logic, API key handling, and storage serialization would benefit from basic tests — particularly verifying that unauthenticated requests to `/api/generate` are rejected (once that's fixed) and that localStorage round-trips handle edge cases (full storage, corrupted JSON).
